当一个后端工程师拿到新产品需求时，最自然的反应往往是：有哪些实体？表之间是什么关系？需要哪些 API？

这些问题没有错。但当我们开始对完整产品负责时，还需要向前多问一步：**我们已经知道用户要解决什么问题，还是只知道怎样把眼前这句话翻译成代码？**

我的判断是：对于用户场景尚不清晰的新产品，应该优先验证问题和关键使用路径，同时尽早检查技术与成本约束。数据库、API 和架构仍然重要，只是不该在缺少证据时替我们定义产品。

这就是本文所说的 Product-First：以用户结果决定工程投入的顺序，而不是规定所有项目都必须先画界面。它适合需求探索，不适合被套用成“设计全部结束，工程才可以开始”的流程。

本文面向开始承担产品责任的后端工程师、全栈工程师和独立开发者。下面用一个假设的项目管理系统贯穿讨论；其中的客户反馈、界面和技术方案用于说明取舍，不是某次真实项目的验证记录。

## 1. 一个自然的起点，也可能是一次过早的承诺

假设客户说：“我需要一个项目管理系统，可以创建项目、分配任务并追踪进度。”

熟悉后端开发的人很容易立刻想到：

```text
User
Project
ProjectMember
Task
Comment
```

接下来是表结构、外键、索引，再接着是接口：

```text
POST   /projects
GET    /projects/:id
GET    /projects/:id/tasks
POST   /projects/:id/tasks
PATCH  /tasks/:id
```

这套设计能够表达项目、成员和任务，也很容易拆成开发任务。问题在于，它悄悄接受了一个尚未验证的前提：客户说的“管理项目”，主要就是管理任务。

进一步交流后，答案也许完全不同。客户最关心的是哪些项目可能延期、哪个里程碑被阻塞、谁有权协调资源；任务分配已经在现有工具里完成，并不需要再做一次。

如果我们已经实现任务分配、评论、通知和看板，这时要调整的就不只是需求文档，还包括代码、测试，甚至已有数据。

真正的问题不是“后端工程师不懂产品”，而是熟悉的技术路径太容易让人产生进展感：表建好了，接口跑通了，系统似乎越来越完整，但它是否解决了正确的问题，仍然没有答案。

## 2. Product-First 改变的是决策依据

我想区分三件经常被混在一起的事：

- 产品问题：谁在什么场景下遇到了什么困难，什么结果才算改善？
- 领域模型：业务概念、行为、规则与约束如何表达？它不仅是实体之间的关系。
- 持久化模型：为了可靠地保存和查询数据，系统采用什么存储结构？

这三者互相影响，但不能互相替代。数据库能够保存一条任务记录，并不意味着用户需要一个新的任务系统；页面上出现“项目健康度”，也不意味着数据库里必须新增一张同名表。

下面比较的是需求不清晰时的两种推进倾向，不是后端开发与产品设计的能力高低。

| 判断维度 | 过早以实现为中心 | 以产品问题为中心 |
| --- | --- | --- |
| 首先确认的问题 | 需要哪些表和接口 | 谁需要完成什么，当前障碍在哪里 |
| 接受什么作为依据 | 功能清单已经确认 | 使用场景、任务观察和技术验证共同支持判断 |
| 如何控制返工成本 | 实现之后再收集整体反馈 | 对最不确定的假设先做小规模验证 |
| 产品与工程如何协作 | 产品给需求，工程接单实现 | 工程约束参与范围取舍，用户反馈修正实现方向 |

因此，Product-First 不是把工程推迟到最后，而是让每一次投入都能回答：它正在降低哪一种不确定性？

如果最大的不确定性是“用户是否需要”，先做完整后端可能太早；如果最大的不确定性是“这个计算能否在预算内完成”，先画十个页面也未必有用。

## 3. 第一步不是画 UI，而是把问题说具体

从 Backend-First 转型时，很容易走向另一个极端：“既然不能先建表，那我先打开 Figma。”

但界面同样是解决方案。“我们需要一个 Dashboard”并没有比“我们需要一张项目表”更接近问题本身。

我更愿意先问清楚四件事：谁使用、什么时候使用、要做什么决定、现在为什么做不好。

在项目管理这个例子里，可以先形成一个待验证的场景：

> 项目经理每天早上需要找出可能延期的项目，理解主要阻塞原因，并确定今天应该找谁协调。

这句话立即改变了设计重点。页面的首要任务不再是完整展示所有项目字段，而是帮助用户识别风险、理解原因和采取行动。

接下来还要追问：项目经理现在怎样完成这件事？需要翻多少份表格、问哪些人？哪些信息经常缺失或过期？实际协调资源的人是否真的是项目经理？提出采购需求的人，也未必是每天使用系统的人。

“成功”也应该在这里开始定义。可以先观察现有流程，再约定可检验的目标，例如找到风险项目并确定负责人的耗时是否下降、关键阻塞是否更少被遗漏。目标需要结合当前基线确定，不能凭空写一个看起来漂亮的提升比例。

## 4. 用用户流程和原型检验理解

明确场景之后，再梳理用户完成任务的路径。省略登录等公共入口，核心流程可能是：

```text
查看风险项目
  -> 进入项目详情
  -> 找到延误的里程碑
  -> 查看阻塞原因
  -> 确认负责人与下一步行动
  -> 跟进处理结果
```

这时先不要讨论 React 组件怎么拆，也不必急着选 REST 还是 GraphQL。更值得讨论的是：用户能否在这条路径上完成决定？是否需要跳回聊天工具才能找到真正有用的信息？

低保真原型只需要承载这些问题。纸笔、静态页面或简单线框图都可以：

```text
Projects at risk
------------------------------------------------
Project   Milestone       Due date   Owner
Apollo    API migration   Oct 21     Unassigned
Mercury   Integration     Nov 02     Team B
------------------------------------------------
Open Apollo
  -> Blocker: access approval pending
  -> Next action: assign a coordinator
```

这不是最终视觉设计，而是一组可以被反驳的产品假设：用户需要按风险找项目；里程碑比任务数量重要；负责人缺失是一条值得突出显示的信息。

假如客户指出“项目经理不能分配这个负责人，必须交给部门经理”，我们就发现了一个权限和业务流程问题，而不只是按钮摆放问题。

### 原型应该接受任务测试，而不只是审美评价

只问“你觉得这个界面怎么样”，很容易得到礼貌性的认可。更有价值的方式是给出一个具体任务：

> “假设你现在准备参加早会，请找出最需要协调的项目，并说明你接下来会联系谁。”

观察用户从哪里开始、如何判断、在哪一步停下、还需要哪些系统外信息。尽量让用户自己完成，而不是由设计者一路解释。

不同原型只能回答不同问题：线框图可以帮助讨论信息结构，可点击原型可以检查路径是否容易理解，但它们不能证明用户会长期使用、愿意付费，或数据在真实环境中足够及时准确。

因此，原型获得好评只是证据的一部分。对价值的判断，还需要结合真实任务、现有替代方案，以及适当规模的试用和后续使用情况。

原型的价值不是“越漂亮越好”，也不是修改永远只要几分钟。它的价值在于：**用与当前问题相匹配的低成本实验，决定下一步是否值得投入。**

## 5. 技术可行性必须提前进入讨论

用户路径再顺畅，也不能证明方案在技术或商业上可行。

假设需求变成“在地图上实时展示一百万台设备的位置”。页面可能只有一张地图，但工程问题已经很重：设备多久上报一次？允许多大延迟？用户真的需要同时看到每一台设备吗？数据能保存多久？谁有权查看精确位置？

做一个粗略量级估算：假设所有设备持续在线，每台每十秒发送一条位置消息，平均就是每秒十万条；改为每秒一条，平均就是每秒一百万条。这还没有计入重试、突发流量和协议开销，也不等于系统应该给每个浏览器推送这么多更新。

这个估算足以触发产品讨论：

- 是否可以只推送当前视野内的数据？
- 低缩放级别是否只需要聚合结果？
- 不同设备是否需要不同刷新频率？
- 哪些操作真正依赖低延迟，哪些只需要近实时概览？
- 地图服务、存储、网络和运维成本能否被业务承受？

这些问题可能需要小规模技术实验、供应商限制核查和成本估算，不能靠原型替代。

同样，也不能直接宣布“十秒刷新和一秒刷新没有体验差异”。对趋势概览可能差异很小，对调度或安全告警可能完全不同。可接受的延迟应当由使用场景和验证结果决定。

## 6. 产品探索与工程探索应当相互反馈

我更认可的方式不是一条从需求到上线、只向前走的流水线，而是两条围绕同一个目标互相修正的工作线：

```text
产品探索                         工程探索
用户问题与成功标准       <---->   数据来源与硬约束
场景、流程、低保真原型   <---->   可行性实验与成本估算
任务验证与范围调整       <---->   业务规则与边界校验
          \                        /
           -> 最小端到端交付范围 <-
                       |
                       v
                实现、测试、小规模发布
                       |
                       v
                观察结果，修正下一轮
```

“双轨”不一定意味着两支团队。独立开发者也可以在两个视角之间切换。关键是让信息尽早流动，而不是让设计稿成为工程只能被动接受的合同。

产品提出实时更新，工程带回延迟与成本的测量结果；工程发现某条流程需要复杂审批，产品重新确认它是否属于首版范围。双方共同决定什么必须保留，什么可以简化，什么需要继续验证。

也不必等所有需求稳定后才交付。在项目管理系统里，可以先完成“发现一个风险项目、明确原因、找到负责人”这条最小闭环，再根据使用反馈决定是否需要任务看板、预算管理或复杂通知。

这里的“最小”指功能范围，不是质量底线。权限、隐私、数据正确性和必要的失败处理，不能因为是 MVP 就被省略。

## 7. 从用户行为反推领域，而不是照着页面建表

随着核心场景越来越清楚，后端工程师熟悉的能力就有了更可靠的落点。

在这个例子中，候选模型可能是：

```text
Project
  -> Membership
  -> Milestone
  -> Risk
```

但这不是照抄导航菜单得到的表清单。每个概念都要继续接受业务问题的检查：

- 里程碑怎样算完成，谁有权修改预期日期？
- 风险有哪些状态，什么条件下允许关闭或重新打开？
- 风险负责人是否必须是项目成员，离职或退出项目后如何处理？
- 谁能看到项目详情，谁能修改风险？
- 哪些变化需要历史记录，哪些操作必须保持一致性？

领域模型也可以更早参与这些讨论。画一张简单状态图、列出几个业务不变量，往往能帮助客户发现流程里的矛盾。需要延迟的不是所有建模，而是把未经验证的假设过早固化成长期契约。

当行为逐渐明确后，再讨论用例和接口。例如，报告风险、指定负责人、关闭风险，可能对应下面这样的接口草案：

```text
POST  /projects/:project_id/risks
PATCH /projects/:project_id/risks/:risk_id
POST  /projects/:project_id/risks/:risk_id/resolve
```

这只是表达业务意图的一种方式，不是生产级接口规范。真正落地时，还要定义请求与响应、错误语义、权限校验、并发冲突处理，以及有需要时的重试与幂等行为。路径里带着项目 ID，也不代表授权已经完成。

同样，页面上的“项目健康度”可能只是根据里程碑延误、未解决阻塞和其他信号计算的展示结果。只有需要历史趋势、追溯或特定查询性能时，才进一步讨论快照、缓存或独立存储。

API 与数据库也未必需要严格谁先谁后。它们可以围绕业务行为共同演进：先明确必须保证什么，再选择表达和保存这些保证的方式。

## 8. 全栈能力，不只是前端加后端

当我们开始对完整交付负责，全栈的价值不只在于能写两端代码，也在于能把一个决定放进不同视角里检查。

以“关闭风险”为例：

| 视角 | 需要追问的问题 |
| --- | --- |
| 产品 | 关闭记录，是否真的代表阻塞已经解除？ |
| UX 与 UI | 用户能否看懂关闭的后果，误操作后能否恢复？ |
| 前端 | 提交中、失败、权限不足和数据过期时如何呈现？ |
| 后端 | 谁能关闭，允许从哪些状态关闭，如何保证规则成立？ |
| 数据 | 是否记录操作人、时间、原因和状态历史？ |
| 架构与运维 | 当前规模需要什么复杂度，出错后如何发现和定位？ |

这不意味着每个人都必须成为所有领域的专家，而是不能因为某个问题不属于自己最熟悉的技术栈，就默认它已经被别人解决。

本文所说的 Product Engineer，是一种责任视角：不仅关心功能是否实现，还关心它是否帮助用户完成目标，以及团队能否持续、可靠地交付它。它不要求取消设计、产品和工程之间的专业分工。

## 9. 这套方法适合什么，不适合什么

### 适合：用户工作方式尚不清楚的新产品

当客户只能给出“我要一个管理系统”这样的描述，或者团队还不知道谁会使用、为什么会使用，先做场景访谈、流程梳理和轻量验证，通常比扩展实体清单更能减少风险。

它也适合成熟产品中的新工作流。已有技术栈不代表新增场景已经成立，旧用户也可能并不需要新功能。

### 不适合：把所有工作都包装成一轮产品探索

修复明确的缺陷、完成确定的协议兼容、执行有验收标准的迁移，不必重新做一遍用户旅程和界面原型。目标已知时，直接分析影响面、实现、验证，往往更合适。

API 平台、基础设施和数据产品同样需要理解用户，但它们的原型可能是一份接口契约、一个命令行演示或一次性能实验，而不是 Figma 页面。技术约束本身可能就是最大的产品风险。

### 边界：改变工作顺序，不废弃工程纪律

对于我的工作流，这个变化不是“不再从模型思考”，而是区分两个层次：在决定做什么时，先确认问题；在决定如何实现时，仍然认真建立模型、状态、规则和不变量。

Product-First 不能代替测试、评审、权限设计或容量规划；Backend-First 也不必然意味着忽视用户。我们需要纠正的是未经验证就开始重投入的习惯，而不是给某一种岗位贴标签。

## 10. 三个容易反复出现的误区

### 把客户提出的功能，当成已经确认的需求

客户说“加一个导出 Excel 按钮”，背后也许是财务每月需要把数据交给负责人。定时报告可能有帮助，但也可能不合适：财务还需要离线调整、合并多个来源，或者遵循固定模板。

追问问题的目的不是替客户换一个更时髦的答案，而是弄清约束之后再选择。导出 Excel 完全可能就是正确方案。

### 用漂亮原型掩盖缺失的数据和流程

界面可以轻松显示进度百分比、风险等级和最新更新时间，但谁提供这些数据，多久更新一次，缺失时怎么办？如果没有可靠来源，Dashboard 只是在更整齐地呈现不可靠的信息。

所以设计字段时，就应同时核查来源、责任人和更新机制，而不是把这些问题留给后端“想办法”。

### 为尚未出现的规模支付架构成本

微服务、消息队列、缓存和复杂读写模型都可能有合理用途，但“以后可能需要”不是充分理由。

我更倾向于先选择满足当前约束的简单结构，保留清晰边界，再根据真实瓶颈演进。用户少也不代表可以忽视安全和一致性；判断复杂度应看业务约束，而不只是人数。

## 11. 下一次接到新需求，可以先检查这些问题

这份清单不是要求每个项目都产出一套文档，而是帮助判断：我们是否有足够证据，进入下一步投入？

### 问题与结果

- [ ] 能否说清楚具体用户、使用时机和要完成的决定？
- [ ] 是否了解当前替代方案，以及它真正不够好的地方？
- [ ] 是否约定了可以观察的成功标准，而不只是功能数量？

### 流程与验证

- [ ] 核心路径能否完成任务，是否依赖未说明的线下环节？
- [ ] 是否让实际使用者尝试过具体任务，而不仅是看过演示？
- [ ] 是否区分了“看得懂”“做得到”和“愿意持续使用”？

### 可行性与范围

- [ ] 关键数据、性能、成本、权限和隐私约束是否明确？
- [ ] 最危险的技术假设是否有适当的实验或核查支持？
- [ ] 首版是否形成一个完整闭环，非必要功能是否可以暂缓？

### 实现与交付

- [ ] 业务规则、状态转换和数据归属是否明确？
- [ ] 是否覆盖空状态、加载、失败、权限不足及关键并发情形？
- [ ] 是否具备必要的测试、监控，以及与风险相称的回退或恢复方案？

### 发布与反馈

- [ ] 发布后由谁观察使用情况和用户反馈？
- [ ] 是否能分清功能被打开，与用户目标真正完成？
- [ ] 什么证据会让我们继续、调整，或者停止这项投入？

## 12. 延迟昂贵的承诺，不延迟学习

如果只能保留一个原则，我会选择：**尽早验证高风险假设，在证据足够时再承担高变更成本的承诺。**

线框图通常容易调整，但做一个精细的假原型也可能很浪费；数据库结构可以迁移，却会随着数据量、业务依赖和运行要求增加而变得更难改；公共 API 能演进，但需要考虑消费者和兼容成本。

所以重点不是机械地“数据库晚一点做”，更不是无限等待需求稳定。真正要判断的是：现在做这个决定，依据是什么？判断错了，修改会影响谁？是否有更小的实验能先减少不确定性？

有些承诺恰恰需要很早明确，例如敏感数据的采集边界、不能违反的业务规则、外部协议和成本上限。Product-First 同样要求尊重这些约束。

对后端工程师来说，这不是放弃自己的优势。我们仍然需要扎实的数据建模、可靠的接口、正确的事务和可维护的架构，只是把它们放到更明确的问题之下。

从 Backend Engineer 走向 Product Engineer，重要的一步，是把提问从：

> How should we build it?
>
> 我们应该怎样实现？

向前移动到：

> Why should we build it, and for whom?
>
> 为什么值得做，为谁而做？
>
> How will we know it works?
>
> 怎样知道它真的解决了问题？

下一次接到新需求，不妨先写下一句话：“谁，在什么场景下，需要完成什么，而现在被什么阻碍。”然后挑出其中最不确定、判断错误代价最高的一个假设，设计一次小验证。

表结构和 API 不会因此失去位置。相反，当我们更清楚为什么要做，它们才有机会成为正确问题的可靠答案。

- [Marty Cagan：The Four Big Risks](https://www.svpg.com/four-big-risks/)：从价值、可用性、可行性和商业可持续性四类风险检查产品决策。本文的原型与技术探索分别只能覆盖其中一部分。
