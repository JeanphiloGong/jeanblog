我目前的判断是：**本地工具优先直接调用；任务方法可以沉淀为 Skill；当同一能力需要被多个 Agent 客户端统一发现和调用时，再考虑 MCP。** 工具调用次数多，并不是迁移到 MCP 的充分理由。

这篇文章适合正在编写 Coding Agent、Skill 或工具集成的开发者。它记录的是我在学习 Agent Runtime 时形成的设计判断，不是对 MCP 市场占有率的调查，也不是生产系统的性能评测。

## 从直接调用工具开始，为什么又出现 MCP？

在一个最小 Coding Agent 中，模型返回 `read_file` 请求，应用程序验证路径、读取文件，再把结果交回模型。工具完全可以是一个普通 Python 函数。

同样，读取 Git 状态也可以直接运行命令。在安装了 Python 和 Git 的仓库目录中，下面的代码即可执行：

```bash
python3 - <<'PY'
import subprocess

result = subprocess.run(
    ["git", "status", "--short"],
    check=True,
    capture_output=True,
    text=True,
    timeout=10,
)
print(result.stdout or "Working tree is clean.", end="")
PY
```

这里没有 MCP，仍然能完成任务。命令使用固定参数列表，没有拼接模型生成的 Shell 字符串；但它也不是沙箱，仍然拥有当前进程的权限。

麻烦通常出现在复用阶段：同一个能力要接入编辑器、桌面助手和自己的 Agent。每个客户端都需要知道工具名、参数、返回格式，以及如何与工具服务通信。如果每一对客户端和服务都单独集成，维护成本就会增加。

MCP（Model Context Protocol）提供标准化的接入协议。支持对应能力的客户端可以查询服务提供的工具及其参数 schema，再通过协议发起调用。服务内部仍然可以执行 Git 命令、调用数据库或访问 HTTP API。

因此，**CLI 和 MCP 可以同时存在：CLI 完成实际操作，MCP 为它提供一种客户端接入方式。** 是否值得增加这一层，要看接入需求，而不是看命令行是否显得“原始”。

## Skill 又解决什么问题？

即使 Agent 已经能调用文件、Git 和测试工具，它也不一定知道怎样完成一次有质量的代码审查：

- 先阅读哪些项目约定？
- 如何确定检查范围？
- 测试失败时，应区分哪些原因？
- 哪些问题值得报告，报告需要什么证据？

这些方法和判断标准适合写进 Skill。

以 Agent Skills 格式为例，一个 Skill 可以包含 `SKILL.md` 中的说明，也可以携带脚本、参考文档和其他资源。支持它的宿主按需加载相关内容。它不是只能装自然语言的容器，更不要求必须通过 MCP 执行操作。

代码审查 Skill 可以指导 Agent 使用本地 Shell、直接工具，也可以使用 MCP 工具。具体可用哪些能力，由宿主和运行环境决定。

| 比较维度 | 直接函数 / CLI | MCP | Skill |
| --- | --- | --- | --- |
| 主要复用对象 | 一段可执行能力 | 客户端与服务之间的接入契约 | 任务方法、领域知识及配套资源 |
| 如何使用 | 程序调用函数或启动命令 | 客户端通过协议发现和调用能力 | 宿主加载说明，Agent 按指导完成任务 |
| 主要维护成本 | 参数、输出、依赖和执行环境 | 另加协议连接、服务生命周期及兼容性 | 说明质量、脚本依赖和宿主能力差异 |
| 不能单独保证 | 任务流程正确 | 授权、隔离或业务语义一致 | 步骤必然执行、权限约束必然生效 |

两者都追求复用，但复用对象不同。MCP 统一接口，并不意味着任意客户端都能无配置地使用任意服务；Skill 可以迁移，也不意味着引用的命令、路径和工具在每个宿主中都存在。

## 编排太多，应该搬到哪里？

“一个 Skill 承担了太多工具编排，是否应该把这些工具做成 MCP？”这个问题需要进一步拆开。

### 重复的机械步骤：先考虑脚本

假设 Skill 中反复写着：

```text
运行三个固定命令
→ 读取它们的退出码
→ 整理输出
→ 按固定规则生成 JSON
```

如果步骤和分支完全确定，让模型每次重新解释它们，未必有收益。可以把这段操作提取为一个脚本，由 Skill 说明什么时候运行、如何解读结果。

这已经消除了重复编排，无需同时引入 MCP。将来有多个客户端需要这一能力，再评估是否给脚本增加 MCP 接口。

### 依赖任务语义的决策：保留在 Skill 和 Agent 中

例如，“这次修改是否涉及数据库迁移，因此需要检查旧数据兼容性”，需要结合改动内容判断。

Skill 可以提供判断依据，Agent 根据上下文决定检查步骤。把底层工具换成 MCP，并不会自动获得这种判断能力。

### 必须可靠执行的控制：放进 Runtime 或工作流代码

超时、重试上限、批准后才能执行、失败后停止后续步骤，都不能只依赖模型记住一段说明。

这些条件应由运行代码落实。Skill 可以解释规则，Runtime 或工作流负责强制执行。MCP 服务也可以实现自身的权限检查，但协议本身不会替应用完成这些控制。

### 多客户端共享的外部能力：考虑 MCP

如果代码审查助手、IDE 和自动化平台都需要访问同一个项目查询服务，MCP 就有明确价值：服务集中维护能力，客户端通过统一协议接入。

工具粒度也不必局限于 `read_file`、`git_diff` 这样的底层操作。一个输入输出稳定的“收集项目检查结果”工具，同样可以是合理的 MCP 工具。服务内部可以编排多个确定性操作。

真正需要判断的是：**这个能力是否有清楚的业务边界，是否值得作为服务被独立复用。**

## 用一次代码审查看清边界

在我的学习项目里，我更倾向于从这样的结构开始：

```text
代码审查 Skill
  描述审查方法、证据标准和报告要求
          ↓
Agent Runtime
  管理模型循环、上下文、工具执行和停止条件
          ↓
  ├─ 本地函数：读取受限目录中的文件
  ├─ 受控 CLI：获取 Git diff、运行测试
  └─ MCP 客户端：访问团队共享的项目查询服务
```

这里没有“所有工具必须经过 MCP”的要求。新增 MCP 服务也不意味着需要把本地工具全部重写。

同样，Skill 中的“运行测试”不代表测试已经执行。执行记录、退出码和结果必须来自实际工具调用。无论选择哪一种接口，都要保留这个事实边界。

## 什么时候适合 MCP，什么时候不适合？

我会用以下问题做选择：

| 当前需求 | 优先考虑 |
| --- | --- |
| 一个本地 Agent 调用已有 Git 命令 | 直接 CLI |
| 多个任务重复运行同一组固定检查 | 脚本或普通函数 |
| 多个 Agent 客户端需要统一接入同一工具服务 | MCP |
| 希望复用代码审查、写作或发布的方法 | Skill |
| 必须保证审批、重试和恢复流程 | Runtime / 工作流代码 |

MCP 尤其适合已经存在独立服务边界、需要跨客户端接入的能力。它不太适合仅为一个进程内部的小函数增加远程调用形式，也不值得仅因为“工具数量变多”就批量封装。

如果现有 CLI 的接口稳定、输出可解析、环境容易复现，那么“Skill + CLI”可以一直是合理方案。它不是等待升级为 MCP 的临时状态。

## 三个容易误解的地方

**Skill 的出现，不代表 MCP 被取代。** Skill 可以使用 MCP，也可以完全不使用。不能仅凭某个产品开始支持 Skill，就推断 MCP 的使用量下降；这需要另外的采用率数据。

**按需加载不等于必然更省 Token。** Skill 的逐步加载有助于控制说明进入上下文的时机，但实际成本还取决于宿主如何加载内容、如何暴露 MCP 工具，以及返回结果有多大。不能把某种加载策略当成两个概念之间的绝对差异。

**统一接口不等于安全边界。** MCP 服务、CLI 和 Skill 附带的脚本都可能访问文件或外部系统。身份认证、授权、审批、凭据管理和沙箱需要具体实现；把操作移到另一个进程中，也不自动构成隔离。

## 我会怎样继续实践

我会先保留能直接工作的工具，观察重复出现的需求：机械操作提取成脚本，任务方法整理为 Skill，跨客户端的接入需求再引入 MCP。必须成立的执行约束则写进程序，并通过测试验证。

如果你正在维护一个很长的 Skill，可以先挑出其中一段工具编排，问自己：它是在表达需要判断的方法，还是在重复一段固定程序？先回答这个问题，再决定是否需要服务化，通常比直接“全部改成 MCP”更有效。
