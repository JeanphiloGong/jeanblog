做登录功能时，我们经常听到这些建议：“用 Session 就够了”“现在都用 JWT”“接企业单点登录”“支持验证码或者 Passkey”。

这些词看起来都在描述登录，却不在同一个层面。密码可以和 Session 一起用，JWT 可以放进 Cookie，企业账号登录后也可以建立应用自己的 Session。

如果你刚开始做账号系统，先别急着在这些名词之间选一个。**先弄清两个问题：用户第一次如何证明身份，之后每次请求如何证明自己已经登录。** 然后再看凭证的格式、传递方式和权限判断。

## 先沿一次登录走完流程

假设小林登录一个收藏网站，然后查看自己的收藏夹：

```text
输入账号和密码
      ↓
后端验证密码，并检查账号是否允许登录
      ↓
创建登录会话，把凭证交给浏览器
      ↓
浏览器请求“我的收藏夹”，携带凭证
      ↓
后端验证凭证，确定当前用户
      ↓
检查这个用户是否有权读取该收藏夹
      ↓
返回数据
```

这里至少有三件事：

- **身份验证（Authentication）**：确认你是谁。第一次可以用密码，后续可以验证已签发的凭证。
- **会话管理（Session Management）**：维护这次登录的有效期、退出和撤销等状态。
- **授权（Authorization）**：判断你能做什么，例如能否读取某个收藏夹。

登录成功不代表后续接口可以跳过认证；身份验证通过，也不代表可以读取别人的数据。前端隐藏按钮不能替代后端授权。

## 第一层：用户用什么证明身份？

这是登录页面最容易看见的区别。

| 方式 | 用户提供的证明 | 适用与取舍 |
| --- | --- | --- |
| 账号密码 | 知道账号对应的秘密 | 通用，但需要密码哈希、找回流程，并应对撞库与钓鱼 |
| 短信或邮箱验证码 | 能取得指定渠道收到的一次性代码 | 免记密码，依赖通信渠道安全、送达率和发送成本 |
| 邮箱登录链接 | 能使用邮箱中收到的一次性链接 | 操作简便，需要限制链接有效期和重复使用 |
| Passkey | 用已注册凭证的私钥完成签名 | 可免密码、抵抗常见钓鱼，需要考虑设备支持和账号恢复 |
| 第三方或企业账号 | 受信任身份提供方完成的认证 | 减少重复注册，增加对提供方及接入流程的依赖 |

**验证码登录并不自动等于双因素认证。** 只输入短信验证码，是一种单因素登录方式；密码加一个独立的第二因素，才可能构成双因素认证。是否独立，取决于所用机制，不能只数页面上有几个输入框。

Passkey 也不等于把指纹上传给网站。通常是设备或认证器通过指纹、面容或 PIN 等方式确认使用者，再用私钥对挑战进行签名。网站保存对应公钥并验证签名，私钥不交给网站。不同产品的凭证可能绑定设备，也可能通过凭证提供方同步，恢复方案仍需单独设计。

无论第一次用哪一种方式验证身份，应用之后都需要决定：下一个请求靠什么识别这个用户？这就进入了会话与凭证设计。

## 第二层：服务端 Session 怎样保持登录？

一种成熟而直接的方案是：**浏览器拿一个不可猜测的随机凭证，服务端保存它对应的会话。**

登录成功后，服务端建立类似这样的记录：

```text
凭证的摘要 → 用户 user-123、到期时间、撤销状态
```

浏览器拿到的是原始随机凭证。后续请求带回来，服务端计算摘要、查询会话，再判断是否过期、撤销，以及账号当前是否可用。保存摘要是保护存储凭证的一种做法，不是 Session 概念唯一允许的实现。

这里的 token 只是“凭证”的统称。一个随机字符串也可以叫 token，不必长得像 JWT。

如果管理员撤销会话，下一次验证时就可以拒绝旧凭证。如果还要求账号禁用后立即停止访问，就需要认证路径检查账号状态，或在禁用时让相关会话失效。

**这些行为要由实现兑现。** 使用 Session 不会自动让密码重置撤销所有设备，也不会自动刷新缓存。如果认证结果缓存了五分钟，撤销可能也要等缓存失效；已经通过检查、正在执行的请求，也不会仅因会话随后被撤销就自动中断。

### Cookie 在这里做什么？

Cookie 是浏览器保存和随符合条件的请求发送数据的机制。它可以装一个随机 Session 凭证，也可以装 JWT。

例如服务端可能发送这样的响应头，下面只是格式示意：

```http
Set-Cookie: session=opaque-random-value; Path=/; HttpOnly; Secure; SameSite=Lax
```

浏览器之后按域名、路径等规则附带 Cookie，后端再验证其中的凭证。

`HttpOnly` 限制网页 JavaScript 读取 Cookie；`Secure` 要求浏览器通过 HTTPS 发送；`SameSite` 控制跨站请求中携带 Cookie 的条件。它们各有作用，不能把其中一个开关当成完整的安全方案。例如使用 Cookie 的状态变更请求仍需按场景设计 CSRF 防护。

Cookie 不是服务端 Session 本身，也不是某种身份验证算法。

## 第三层：JWT 与随机凭证有什么区别？

JWT，全称 JSON Web Token，是一种携带声明的令牌格式。它可以表达“这个凭证针对哪个用户、由谁签发、给谁使用、什么时候过期”。

例如，下列内容只是 JWT 载荷的示意，**不是一个可直接使用的 JWT**：

```json
{
  "sub": "user-123",
  "iss": "https://identity.example.com",
  "aud": "collection-api",
  "exp": 2000000000
}
```

这些字段分别表示主体、签发者、接收方和过期时间。`exp` 使用 Unix 时间戳，单位是秒。

常见的签名 JWT 将头部、载荷和签名编码为一个字符串。接收方验证签名，并按应用约定核对算法、签发者、接收方和有效期等，才能信任其中的声明。**解码出 JSON 不等于验证通过。**

签名 JWT 的载荷通常可以直接解码查看，签名保护完整性，不负责保密，因此不应放密码等秘密。JWT 标准也支持加密形式，但不能因为名称叫 JWT 就默认内容已经加密。

和随机凭证相比，主要差别在于后端如何取得可信信息：

| 对比 | 随机凭证 + 服务端 Session | 本地验证签名的 JWT 访问令牌 |
| --- | --- | --- |
| 凭证表达什么 | 用于查找服务端记录的随机值 | 携带用户、有效期等声明 |
| 每次请求怎么认证 | 查询会话并检查相关状态 | 验证签名及所需声明 |
| 对身份服务的依赖 | 常需要在线查询，可通过共享存储或身份服务完成 | 验证密钥已缓存时，可不逐次查询身份服务 |
| 立即撤销 | 更新服务端状态，下一次有效查询可见 | 纯本地验证无法得知刚发生的撤销，需额外机制 |
| 状态是否能变化 | 可在查询时读取最新状态 | 令牌中的声明保留签发时的信息，除非另外查询 |

这是两种具体用法的比较。**JWT 本身没有规定你必须无状态，也没有禁止查询数据库。** 它可以配合撤销列表、令牌内省或账号状态查询；只是这样也会引入状态与在线依赖。

### 为什么退出登录在 JWT 场景里更容易被误解？

假设一个访问令牌还有十分钟才过期。用户退出时，浏览器删除了它，但别人此前复制的那份仍可能通过验签。

删除客户端凭证，和让服务端拒绝所有副本，是两件事。

可以采用较短的访问令牌有效期、撤销记录或当前账号状态检查来处理相关需求。常见的访问令牌与刷新令牌组合中，撤销刷新令牌能阻止继续换取新令牌，**却不一定让已签发的访问令牌立即失效**。需要多快失效，应先作为产品和安全要求说清楚。

## 第四层：第三方登录、OAuth 和 OIDC 怎么配合？

“使用企业账号登录”和“让一个应用读取我的云盘文件”看起来都要跳到另一个网站，但目标不同。

**OAuth 2.0 主要处理委托授权**：允许一个应用在一定范围内访问资源，而不用把用户密码交给这个应用。**OpenID Connect（OIDC）在 OAuth 2.0 之上增加身份认证能力**，用来让应用确认登录用户。

OIDC 中两个容易混淆的令牌是：

- **ID Token**：向客户端应用表达这次身份认证的信息，采用 JWT 格式。
- **Access Token**：用于访问目标资源服务器；格式由体系设计决定，可以是 JWT，也可以是不透明字符串。

不能因为 ID Token 里也有用户 ID，就把它拿去当任意 API 的访问凭证。它的接收方和用途不同，资源服务器应验证自己约定的访问令牌。

一次企业登录可以这样组合，下面省略协议报文细节：

```text
用户点击“企业账号登录”
        ↓
应用将浏览器引导至企业身份提供方
        ↓
身份提供方完成认证，按协议返回授权码
        ↓
应用完成授权码交换，验证 OIDC 返回的身份信息
        ↓
映射到本应用的用户，建立自己的 Session
        ↓
浏览器后续携带本应用 Cookie 访问
```

完整接入还需要处理回调关联、PKCE、令牌验证等协议要求，应使用维护中的库或身份平台。上图用于认识数据流，不是手工实现登录协议的步骤清单。

**单点登录（SSO）描述的是一次认证后能访问多个应用的体验。** OIDC 可以支持这种体验，SAML 也是企业场景常见的协议。SSO 与“应用用不用 Session”并不矛盾；退出某个应用，也不一定会退出身份提供方和其他应用。

并非所有“第三方登录”产品都遵循完全相同的协议，具体接入仍应以提供方文档为准。

## 一个小实验：凭证还在，为什么访问却被拒绝？

用 Node.js 可以观察服务端 Session 的核心行为。把下面代码保存为 `session-demo.cjs`，执行 `node session-demo.cjs`：

```js
const { randomBytes, createHash } = require("node:crypto");

const user = { id: "user-123", active: true };
const sessions = new Map();
const digest = (token) =>
  createHash("sha256").update(token).digest("hex");

// 假设身份验证已经通过；这里只演示签发和验证会话。
const token = randomBytes(32).toString("hex");
sessions.set(digest(token), {
  userId: user.id,
  expiresAt: Date.now() + 60_000,
});

function authenticate(token) {
  const session = sessions.get(digest(token));
  if (!session || session.expiresAt <= Date.now()) return null;
  if (session.userId !== user.id || !user.active) return null;
  return user.id;
}

console.log("登录后：", authenticate(token));
user.active = false;
console.log("禁用后：", authenticate(token));
user.active = true;
sessions.delete(digest(token));
console.log("撤销后：", authenticate(token));
```

输出：

```text
登录后： user-123
禁用后： null
撤销后： null
```

凭证字符串始终没有变。访问被拒绝，是因为每次 `authenticate` 都重新检查会话和账号状态。

这个内存实验没有实现 HTTP、Cookie、密码验证、持久化或多实例协调，仅用于观察会话验证规则。它也没有实现某个业务资源的权限检查，认证返回用户 ID 后，还要继续授权。

## 业界怎么选？先列需要保证的行为

这些机制都很成熟，组合方式取决于场景，不能仅凭“JWT 更新”或“微服务更多”来判断。

| 需求 | 常见的起点 | 需要继续确认的行为 |
| --- | --- | --- |
| 自己的网站或管理后台 | 密码、验证码或 Passkey + Cookie + 服务端 Session | 会话过期、账号禁用、退出和改密后的撤销 |
| 企业统一账号接入 | OIDC 或 SAML + 应用自身的会话 | 用户映射、权限分配、应用退出与统一退出 |
| 第三方应用访问 API | OAuth 体系下的访问令牌 | 授权范围、接收方、撤销和令牌生命周期 |
| 移动端或多个 API 服务 | 结合场景采用会话凭证或访问令牌 | 凭证存储、本地验证需求及身份服务可用性 |

如果当前需求是浏览器登录，并且特别关注退出、禁用和密码重置后的及时撤销，**随机凭证 + HttpOnly Cookie + 服务端 Session 是合理的起点**。实际需要把相应的撤销路径实现并验证好。

多实例部署时，会话可以放在共享数据库或合适的共享存储中，不要求请求永远落在同一台服务器。采用 JWT 也不意味着系统完全不需要状态：用户、权限、刷新令牌和撤销信息仍可能需要存储。

对于通过 gRPC 拆分的用户服务，业务服务也可以在线验证会话。是否改用本地验签，要结合延迟、可用性和撤销要求判断，而不是由 gRPC 或“微服务”这个名字决定。

这篇的起点来自 [Session/JWT 学习跟进项 #414](https://github.com/JeanphiloGong/tsingai-lens/issues/414)。这里整理的是通用机制与选型依据，没有审计 Lens 的实际实现，不能据此断言其撤销、Cookie 或权限检查已经全部达标。

设计自己的登录系统时，可以先回答：用户靠什么证明身份，后续请求携带什么，服务端怎样验证，退出后多久拒绝旧凭证，以及认证通过后还要检查哪些权限。把这五个问题连起来，比单独问“用 Session 还是 JWT”更容易得到可执行的方案。
